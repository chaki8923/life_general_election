SEC-01 HIGH 鍵管理

Gemini API キーがクライアントバンドルに焼き込まれている

現状
EXPO_PUBLIC_ 接頭辞の環境変数は Expo がビルド時にバンドルへインライン展開します。 ビルド成果物を実際に検索したところ、AIzaSy… 形式のキーが 2 種類含まれていることを確認しました。 うち 1 つは Firebase Web API キー（公開前提の識別子なので問題なし）、もう 1 つが Gemini のキーです。 さらに URL のクエリパラメータとして送信されるため、プロキシログにも残りやすい形になっています。 
const API_KEY = process.env.EXPO_PUBLIC_GEMINI_API_KEY;
const res = await fetch(`${ENDPOINT}?key=${API_KEY}`, { … });
リスク
アプリバイナリまたは web バンドルを入手した第三者が、Gemini の課金枠を無制限に利用できます。クレジット枯渇・想定外の課金に直結します。
推奨対応
即時：該当キーをローテーションし、Google Cloud Console で Generative Language API のみに用途を絞る。
恒久：Cloudflare Worker または Cloud Functions を挟んでサーバ側で鍵を保持する。
公平を期すための補足

これは無自覚な漏洩ではありません。docs/implementation-plan.md に「ハッカソン速度優先でクライアントから直接呼ぶ／キー露出リスクは認識した上で、本番化する場合は Cloud Functions 経由に移す」とリスク込みの判断として記録済みです。

加えて Gemini 呼び出しは src/services/ai/ のサービス層に隠蔽されているため、差し替えは 1 ファイルの置き換えで済みます。意図的なトレードオフと、移行しやすい構造の両方が揃っている状態です。ただし鍵のローテーションだけは先に済ませてください。

src/services/ai/gemini.ts:1,18 — 実証: dist/_expo/static/js/web/entry-*.js

SEC-03 MEDIUM Firestore

themeStats ルールが count 以外を検証していない

現状
create は count == 1、update は count が +1 であることだけを検証しています。label / category の型・長さ・キー集合は未検証で、themeId にも制約がありません。
リスク
count さえ条件を満たせば、任意のフィールドを最大 1MB まで書き込めます。ランキング表示名の改ざんや不適切な文言の混入、任意 ID のドキュメント無限生成によるストレージ肥大が成立します。
現状のアプリコードは固定カタログ値しか渡していないため、実際の混入は発生していません。
推奨対応
キー集合と ID を許可リストで固定します。 
allow create: if request.auth != null
  && themeId in ['money','love','career','health','hobby',
                 'growth','relationship','other']
  && request.resource.data.keys().hasOnly(['label','category','count'])
  && request.resource.data.count == 1
  && request.resource.data.label is string
  && request.resource.data.label.size() < 50;
