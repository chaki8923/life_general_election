自動化の配線図

このリポジトリには独立した4本の自動化が通っています。何がきっかけで動き、どこで通し、どこで止まるのか。 入口（Teams での依頼）から出口（手元のワークツリー）まで、実装ファイルに紐づけて並べたリファレンスです。

  • GitHub Actions PR の自動マージ

    CI と AI レビューの両方を通った auto-merge ラベル付き PR だけを squash merge。

  • ローカル 開発環境への自動取り込み

    main の更新を60秒ごとに検知して、作業ブランチへ安全にマージ。

  • ローカル → Teams Expo 起動通知

    トンネル URL と QR コードを Teams のグループチャットへ自動投稿。

  • Teams → GitHub 依頼から issue を作る

    Cloudflare Worker が受けて @claude 付き issue を立て、実装を起動。

全体像

4本は一本道につながっているように見えますが、実際に結ばれているのは origin/main の SHA だけです。 手前が止まっても後ろは動きます。

Expo 起動通知だけはこの流れの外側にいます。 他の3本が「依頼 → コード → main」の一方向なのに対し、こちらは開発サーバーの状態を Teams へ流す逆向きの配線です。

GitHub Actions

1. PR の自動マージ

GitHub Free プランでは標準の auto-merge が使えないため、ワークフローで自前実装しています。 関門は CI と AI Review Gate の2つ。両方が「今の SHA で」成功していなければマージされません。

マージの判定 — auto-merge.yml

CI または AI Review の完了（workflow_run）で起動します。PR 番号を指定した手動実行も可能です。 以下をすべて満たさないと、何もせず終了します。

条件満たさないとき
1head SHA に一致する open な PR がある対象なしとしてスキップ
2Draft ではないスキップ
3auto-merge ラベルが付いているスキップ
4check-run lint-and-typecheck が successスキップ
5commit status AI Review Gate が successスキップ

4と5は、起動のきっかけになった SHA ではなく「その時点の最新 SHA」で取り直して判定します。 レビュー中に push された未検証のコミットが、古い成功結果に便乗してマージされるのを防ぐためです。

通過したら gh pr merge --squash --delete-branch。ブランチはそのまま削除されます。

関門その1 — CI（ci.yml）

PR と main への push で npx tsc --noEmit と npm run lint を実行するだけの単純なジョブです。 判定に使われるのはジョブ名 lint-and-typecheck の結果です。

関門その2 — AI レビュー（ai-review.yml）

Codex が読み取り専用でレビューし、問題があれば Claude が直して再レビュー。3回直しても残るなら人間に渡します。

  1. レビュー対象か判定する

    open / 非 Draft / base が main / 同一リポジトリのブランチ / auto-merge ラベルあり / ai-review-blocked なし。 このすべてを満たすときだけ先へ進みます。

  2. AI Review Gate を pending にする

    レビュー中はマージ判定が通らない状態を明示します。

  3. Codex がレビューする

    報告されるのは P0（重大な security / data-loss / availability の欠陥）と P1（実際に起きうるバグ・破綻したユーザー動線）のみ。 スタイルの好みや任意のリファクタは対象外です。指摘は PR のインラインコメントとして投稿されます。

    • 指摘ゼロGate を success にし、auto-merge ワークフローを明示的に再起動してマージへ。
    • 指摘あり自動修正へ進む（3回まで）。
  4. Claude が指摘だけを直す

    ai-review-attempt-N ラベルで回数を数えながら、指摘された箇所だけを最小の変更で修正し、 型チェックと lint を通してから既存の PR ブランチへ直接 push します。新しい PR は作らず、ワークフローファイルも触りません。 その後、自分でレビューを再実行します。

  5. 3回で打ち切る
    • 打ち切り時Gate を failure に、auto-merge ラベルを外して ai-review-blocked を付与。PR にコメントし、Teams にも通知します。

    手動で直したあと auto-merge ラベルを付け直すと、ai-review-blocked と回数ラベルが自動で外れてレビューが再開します。

マージ完了通知が2か所にある理由

notify-teams-on-merge.yml は PR のクローズ（マージ済みのみ）で発火しますが、 GITHUB_TOKEN で行ったマージは他のワークフローを起動しません。 そのため自動マージ経路では発火せず、同じ通知が auto-merge.yml の中にも埋め込まれています。

ローカル / scripts/auto-sync.js

2. 開発環境への自動取り込み

main に入った変更を、手元のリポジトリへ降ろしてくる仕組みです。 GitHub 側の自動マージとは完全に独立していて、見ているのは origin/main の SHA だけ。 誰がどうやって main を更新したかは問いません。 

# 1回だけチェックして終了
npm run sync

# 60秒間隔で監視し続ける（開発中に別ターミナルで起動しておく）
npm run sync:watch

1周回でやること

  1. origin/main を fetch する

    ネットワーク断などで失敗しても、警告を出すだけで次の周回に回します。

  2. ローカル main を最新にする

    今どこにいるかで手段が変わります。main にいるなら git merge --ff-only、 main 以外にいるなら git fetch origin main:main で checkout せずに fast-forward します。 作業ブランチを離れずに済ませるための使い分けです。 ここが失敗（origin と分岐している）しても、作業ブランチへの取り込みは続行します。

  3. 作業ブランチへマージする

    git merge --no-edit origin/main。 main 上にいるとき、detached HEAD のとき、すでに最新のときは何もしません。

マージせず通知だけ出すケース

壊れた状態のワークツリーを黙って残さないための安全弁です。

状況ふるまい
追跡ファイルに未コミット変更がある スキップ。未追跡ファイルだけなら続行します。コミットすれば次の周回で自動的に取り込まれます。
merge / rebase が進行中 スキップ。.git 内の MERGE_HEAD / rebase-merge / rebase-apply の有無で判定します。
マージがコンフリクトした git merge --abort で元の状態へ巻き戻し、手動対応を促します。
ローカル main が origin と分岐している 「要確認」を通知。fast-forward できないので触りません。

通知とループ

結果はコンソールと macOS の通知センター（osascript、macOS 以外では無視）に出ます。 通知は origin/main の SHA と種別の組み合わせごとに1回だけ。 60秒おきに同じ警告が鳴り続けることはありません（ログには毎回出ます）。 ループは setInterval ではなく逐次 setTimeout で、 fetch や merge が60秒を超えても周回が重ならないようにしています。

ローカル → Teams / scripts/start-tunnel-notify.js

3. Expo 起動通知

開発サーバーを立ち上げると、接続用の QR コードが Teams のグループチャットに届きます。 チームの誰でも、その場で実機からアプリを開けるようにするための配線です。 

npm run start:tunnel

# expo への追加引数はそのまま渡せる
npm run start:tunnel -- --port 8082

起動から通知まで

  1. .env を読む

    シェルで export 済みの値は上書きしません。ファイルが無くても正常系として続行します。

  2. expo start -c --tunnel を起動する

    出力は素通し（stdio: 'inherit'）。 stdout をパースしないのが設計上の肝です— pipe すると Expo CLI が非対話モードになり、QR もキー操作も全部消えてしまいます。

  3. ngrok のローカル API を叩いて URL を探す

    http://127.0.0.1:4040/api/tunnels を2秒間隔でポーリング（最大180秒）。 起動直後は接続拒否になりますが、次の周回で拾います。

  4. 自分のトンネルか確かめる

    .expo/settings.json の urlRandomness と突き合わせ、 別プロジェクトや古いプロセスが張った ngrok トンネルを誤検出しないようにしています。

  5. Teams へカードを送る

    「今から開発します！」の見出し、起動者名と時刻、exp:// URL のテキスト、そして QR 画像を載せた Adaptive Card。 QR が主動線です — exp:// リンクは Teams デスクトップ版では開けないことがあります。

  6. 停止したら停止カードを送る

    Ctrl+C で止めると、QR なしの停止カードが同じチャットに届きます。 送られるのは起動通知を送ったセッションだけ。kill -9 や ターミナルの強制終了ではプロセスが即死するため送れません。

設定

# .env（gitignore 済み）
TEAMS_WEBHOOK_URL=<Power Automate の HTTP POST URL>
TEAMS_NOTIFY_NAME=chaki   # 省略時は OS のユーザー名

TEAMS_WEBHOOK_URL が未設定なら、警告を出して通知だけスキップし、expo は通常どおり起動します。 通知の送信に失敗した場合も expo は落ちません。

Power Automate 側で詰まりやすい2点

トリガーの「このフローをトリガーできるユーザー」は必ず「誰でも」にする。 「テナント内すべて」にすると OAuth トークンが必須になり、401（DirectApiAuthorizationRequired）で弾かれます。

アダプティブカード欄は fx（式）タブから入力する。 triggerBody()?['attachments'][0]['content'] を直接タイプするとプレーンテキスト扱いになり、 「message body is invalid JSON」で失敗します。コードビューで先頭に @ が付いていれば正しく入っています。

QR 画像は quickchart.io で生成しています。 つまりトンネル URL が外部サービスに渡ります。exp.direct の URL は URL を知っていれば誰でも到達できる一時的なものなので許容範囲ですが、 気になる場合はカード内の URL テキストだけを使ってください。

Teams → GitHub / cloudflare-worker

4. 依頼から issue を作る

「こう直してほしい」を投げると、@claude 付きの issue が立ち、実装から PR 作成までが自動で走り出します。 中継役は Cloudflare Worker（無料枠 10万リクエスト／日）です。

issue から先 — claude.yml

本文かタイトルに @claude を含む issue（コメント、PR レビューコメントでも可）で起動します。 ワークフロー内の指示で、次のことを守らせています。

  1. Expo v57 のドキュメントを参照し、日本語で応答する
  2. issue に Figma URL があればデザインを実際に見る

    Figma REST API で色やサイズを取得し、レンダリング画像をダウンロードして目視で確認してから実装に反映します。 URL が無ければこの手順は飛ばします。

  3. 自分で PR を作る

    型チェックと lint の通過を確認して push したあと、「手動 PR 作成リンクの案内は禁止」として gh pr create --label auto-merge を必ず実行させます。ラベルが無ければ先に作成します。 — ここで付く auto-merge ラベルが、そのまま1本目の自動マージにつながります。

Teams から Worker への直結はまだ完了していません。 Power Automate の HTTP アクションが有料プラン（Premium）の機能のためです。 現状の運用は次の2つ。

① GitHub の Web UI やモバイルアプリから @claude 付きの issue を作る
② Worker を curl で直接叩く 

curl -X POST "https://teams-to-github.<subdomain>.workers.dev" \
  -H "Content-Type: application/json" \
  -H "x-shared-secret: <SHARED_SECRET>" \
  -d '{"text":"投票結果画面の背景色を変更","user":"chaki"}'

ちなみに Expo 起動通知が無料枠で動くのは、向きが「外部 → Teams」で、プレミアム不要の Webhook トリガーを使えるからです。 issue 作成側は向きが逆なので、同じ手は使えません。

CI が通ることと、正しく動くことは別です。 lint と型チェックを通過しても機能的に間違っている可能性は残ります。 本番デプロイは手動トリガーにして、「main にマージされた＝本番に出た」にしない運用が前提です。

対応する実装: .github/workflows/（ci / ai-review / auto-merge / claude / notify-teams-on-merge）、 scripts/auto-sync.js、scripts/start-tunnel-notify.js、cloudflare-worker/src/index.ts。 セットアップ手順の詳細は docs/automation-setup.md にあります。
